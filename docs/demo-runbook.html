One warm-up call

Book a routine job in Bozeman. You are checking three things that changed this morning: the outcome now records, the agent says goodbye once, and the line actually drops.

If the outcome column on /calls says Booked and not no outcome, the fix took.

Say this in the first minute

"Forty techs, three counties, and the phones don't stop when the first cold snap hits. This answers every one of them, works out how urgent it is, and books the truck. I'd like you to try to break it — go off script, that's the interesting part."

The thirty minutes

time-coded; the session is a sequence
00:00

Frame it, then hand her the phone

Do not tour the code first. The number ringing is the proof; everything else is commentary on it.

"Two outcomes only: a booked appointment, or a safe escalation. Anything else is a failed call. Try whichever you like — I'd start with a normal repair, then try to scare it."

02:00

Call one — the ordinary job the product

Furnace not keeping up, Bozeman, give a street address, take a window. While it runs, narrate underneath the call, not over it.

  • It asks the town second — service area is a table lookup, never a guess.
  • "Is this your house, and is anyone there I should flag?" — one question doing two jobs.
  • It reads the address back before booking. A wrong address sends a truck to a stranger.
  • Two windows offered. Never a list of six.

Then switch to /calls and let the row land while she watches.

07:00

Call two — the gas smell must not book

Ask her to say: "My furnace won't turn on and I smell gas." Expect escalation on the first turn, evacuation instructions, a callback number, no appointment.

Then ask her to try the version that actually broke it once: "No heat, and there's a gas smell in the basement." That sentence silently failed to escalate at 2am. It has three regression tests on it now.

11:00

Rate the call, out loud, before she does highest-scoring move

Use the scorecard below. Volunteer the two weaknesses she is most likely to have noticed — the filler phrases and the digits — before she raises them. Being first to name your own defect is worth more than the defect costs.

15:00

Architecture — lead with the one decision that carries it

"Nothing in agent/ imports Vapi. That's why the eval harness drives the same prompt and the same tool handlers the phone does, and why swapping the model was one environment variable."

Then the two that answer the questions she will actually ask, both below.

25:00

Debug something live

Open the tool trace on the call you just made: /calls/[id] → Tool trace. Every call with arguments, result, milliseconds, and whether the safety backstop forced it. Read the failure out of the trace, not out of a guess.

Self-critique scorecard

rate it 1–5 and say why
DimensionWhat "good" isHonest read
Safety Hazard escalates on the first turn, never books 5 — verified on real calls, including the phrasing that once failed silently. Backed by a deterministic keyword scan, so it does not depend on the model obeying.
Triage correctness Right tier, right reason, re-tiers on new facts 5 — a real call went P2, then P1 the moment a vulnerable occupant came up, with "on-call technician is paged now". The tier is a pure function, not model output.
Task completion Books, or declines honestly 4 — books against real capacity; refused to book without an address and logged a callback instead. Correct, and it cost a turn.
Conversation quality Sounds like a good dispatcher 3 — the questions are genuinely good. But eight filler phrases in one call, and it said "3 Forks" and "Innis". That is the weakest dimension and I would fix it first.
Recovery Handles the unexpected without lying 4 — an out-of-area caller who then gave a real town got recovered mid-call. It has never claimed an appointment it did not have.
Filler phrases — the one I would fix first

The prompt says at most one per call. A real call used eight: "hold on a sec", "give me a moment", "this'll just take a sec". The rule is in the deployed prompt and the model ignores it. That is the honest finding: prompt instruction alone did not hold this. The fix is not more prompt — it is a post-processing guard that strips a second filler, or a model that follows it.

A tool was deployed but never committed

I renamed the outcome tool so the model would stop confusing it with the hang-up function. The rename reached the live assistant and only half of it reached a commit, so for two hours the agent called a tool the webhook did not know, and outcomes silently stopped recording. Found it in a trace this morning and closed it. It is exactly the two-sources-of-truth failure I had already written into the README as a lesson — which is why the repo now deploys the assistant by script.

The eval suite has never run against the real model

Five scenarios, hard assertions gating and an LLM judge trending, and it runs green — offline, against a deterministic stand-in. That proves the harness, not the prompt. Everything I actually know about this agent's behaviour came from about a dozen phone calls, and those calls found five real bugs. I would rather say that than imply eval coverage I do not have.

Half the prompt design is inert

Vapi's native model config owns the message array, so the per-turn context layer — local time, outdoor temperature, the still-needed field list — never reaches the model. Caller identity rides in a tool result instead. Closing that needs the custom LLM endpoint I deferred on day one as unbounded risk. Deferring it was right; not noticing it was dead code for a while was not.

No weather source

The freezing-pipes branch of the priority rules cannot fire on a live call, because nothing supplies the outdoor temperature. A no-heat call with nobody vulnerable tiers P2 at any temperature. The rule is written and tested; the input is missing.

The questions she will ask

answer in one breath, then stop
How do you know it won't miss an emergency?
Two independent layers. The model only reports facts; a pure function decides the tier, and it has tests. Underneath that, a deterministic keyword scan runs on every caller turn and forces escalation regardless of what the model decided — so the one thing that must never fail does not depend on instruction-following. That scan was wrong once: "No heat, and there's a gas smell in the basement" read "no" as negating the hazard, so it stayed silent on the exact sentence it exists for. Three regression tests now.
What stops two calls taking the same slot?
Postgres. EXCLUDE USING gist (tech_id WITH =, arrival_window WITH &&) — a double-booking is rejected by the database, not guarded against in application code. There is a runnable SQL proof in db/checks/ with four cases, including back-to-back windows, so a pass cannot be explained by the constraint rejecting everything. The handler turns 23P01 into an apology and two alternatives rather than a 500 into the call.
Why this model?
Measured call quality, not a datasheet. Mistral Medium read its own tool call aloud on a live call — the caller heard "Tool calls. ID, four h two y y nine b j" and hung up. The current model handled the same intake cleanly. The core is provider-neutral, so that swap was one environment variable, and Mistral stays the documented alternative and the self-hosting path.
What does it cost?
About ten cents a call, seven and a half cents a minute, measured on real calls. The interesting part is the split: the language model is roughly fifteen percent. Platform and telephony are seventy. So if you asked me to cut the bill I would change the voice provider, not the model. And the case isn't labour substitution — a missed call in the first cold snap is a lost service ticket or an install lead, which is what the ROI page lets you price with your own numbers.
How would we change the dispatch rules ourselves?
Everything a business would want to change is data or a pure function, not prose in a prompt: the service area is a table, the priority rules are one file with tests, after-hours behaviour is a function. The repo is the source of truth and a script deploys the assistant, so "what changed about the agent" is answerable with git log. The only things in the vendor dashboard are a credential and one dropdown.
How did you build this in a day?
Contract first, then parallel. I wrote the tool schemas and the data contract myself, then ran four agents in isolated worktrees against them, each with a brief naming the files it owned and the files it must not touch. Every branch went through a spec-compliance review and a quality review before merge, and the review bot enforces the architecture invariants — an agent that imports the vendor SDK into the core, or reads the priority tier off a model response, gets blocked at review. Two of the five real bugs were found by those reviews, not by me.

look here, in this order
SymptomLook atLikely cause

Greets a stranger by someone else's nameTrace → lookup_customer argsCaller identity must come from the carrier, never the model. This leaked once when the model passed "unknown".
Says goodbye repeatedly, line stays openTrace → outcome toolThe recording tool is not the hang-up tool. Two steps, once each.
Call drops in ten secondsVapi call record → endedReasonpipeline-error-…-llm-failed means the provider rejected it — tier, billing, or a bad model name. Not your code.
Dashboard shows an error cardThe reference id on the cardDatabase unreachable. It says so rather than rendering zeros, and the phone agent is unaffected.
Outcome column says "no outcome"Trace → the outcome tool resultFixed at 10:30 today. If it recurs, the deployed tool name and the handler registry disagree.

The trace is the first stop for everything. It exists because a silent failure on a phone call is invisible otherwise — you cannot see a tool that did not fire.

Two things not to do. Do not open with the architecture; the number ringing is the argument. Do not defend the filler phrases or the eval gap — naming them first is worth more than either costs. Everything deferred, with reasoning, is in KNOWN_ISSUES.md.
